## 1. Общие сведения о проекте

### 1.1. Проблема
Заказчик ведёт учёт льготного лекарственного обеспечения пациентов вручную: по каждому пациенту — документ Word «План диспансерного наблюдения», в котором перечислены потребности (назначения препаратов с нормами выдачи) и журнал выдач с вручную вычисляемой датой «обеспечен до». Ручной подсчёт медленный и приводит к расхождениям: даты в разных записях считаются по-разному. Фото рецептов хранятся разрозненно, срок действия рецептов отслеживается по памяти.

### 1.2. Назначение приложения
Единый карманный инструмент фельдшера, который:

1. хранит базу пациентов с их потребностями (назначениями) и нормами выдачи;
2. ведёт журнал выдач препаратов и расходных материалов;
3. автоматически рассчитывает дату «обеспечен до» — до какого числа пациенту хватит препарата;
4. подсвечивает заканчивающиеся запасы и присылает push-уведомления;
5. хранит фото рецептов, распознаёт текст рецепта с фото и следит за сроком их действия;
6. выгружает редактируемые документы Word: «План диспансерного наблюдения» по пациенту и «Сводную потребность» по всем пациентам;
7. делает резервные копии базы «умным» способом (одна полная копия + изменения).

### 1.3. Пользователь и масштаб
- Один пользователь (заказчик), одно устройство (личный телефон), вход по паролю не требуется.
- База: 30–100 пациентов; у пациента от 1 до ~15 назначений; история выдач — до нескольких сотен записей на пациента.
- Пациенты — в основном дети, в том числе льготники (например, инвалиды с сахарным диабетом), и обычные граждане, нуждающиеся в лекарственном обеспечении. Данные персональные и чувствительные.

### 1.4. Ключевые ограничения
- **Полностью офлайн:** ни одна функция не требует сети; приложение не отправляет данные наружу (никакой аналитики, телеметрии, облачных сервисов).
- **Данные только на устройстве:** база и фото хранятся в приватном хранилище приложения; резервные копии — файлами в каталоге, выбранном пользователем.
- **Русский язык** интерфейса и документов.
- В объём проекта НЕ входят: многопользовательность, синхронизация между устройствами, серверная часть, публикация в Google Play, поддержка нескольких медицинских организаций, парольная защита и шифрование базы (решение заказчика: телефон личный).

| Дата рождения | да | В списках показывать возраст |
| Адрес | да | |

| Дата начала заболевания | нет | |

| Представитель (родитель) | нет | ФИО + один или два телефона; тап по телефону — звонок через системный набор номера (`ACTION_DIAL`, без разрешения `CALL_PHONE`) |

### 3.2. Препарат (пополняемый пользователем справочник)

| Поле | Обязательность | Примечание |
|---|---|---|
| Название | да | Например «Фиасп», «Тест-полоски OneTouch Select Plus», «Нутризон Эдванс», «Микролакс», «Спирт медицинский» |
| Категория | нет | Лекарство / расходник / питание — свободный выбор |
| Единица выдачи | да | Упаковка / флакон / банка / штука |
| Штук в упаковке | да (если уп.) | «уп. №5» = 5 картриджей; «уп. по 50 шт» = 50 полосок; «№1» = 1 флакон |
| Концентрация, МЕ/мл | нет | Для инсулинов |
| Объём, мл | нет | Картридж инсулина или флакон (например, спирт 100 мл) |
| Концентрация, % | нет | Для спирта и подобных (70 %) |
| МЕ в штуке | вычисляемое | концентрация × объём, если оба заданы; картридж 3 мл × 100 МЕ/мл = 300 МЕ |

Пример выдачи спирта: «70 % 100 мл №1, количество 2» означает 2 флакона. Спирт ведётся по норме «1 флакон в месяц».

Препараты добавляются пользователем прямо в приложении (заказчик явно просил уметь добавлять новые препараты при изменении назначений специалистов). Справочник — общий для всех пациентов. Препарат можно архивировать (скрывается из выбора). Правила создания и удаления — п. 5.9.

### 3.3. Назначение (норма выдачи)

Назначение связывает пациента и препарат и несёт одну или несколько **записей нормы**. Запись нормы — одна «версия» нормы с датой начала `validFrom`. Изменение нормы создаёт новую запись, старая не удаляется (история сохраняется).

Запись нормы содержит:
- **штучную часть** (необязательно): вид и количество:
  - а) N штук в день («8 полосок в день»);
  - б) N штук в месяц («10 картриджей в месяц», «31 банка в месяц»);
  - в) N штук в год («52 штуки в год»);
  - г) N штук каждые X дней («1 доза в 2 дня», «1 штука в 7 дней»);
- **МЕ-часть** (необязательно): д) N МЕ (ЕД) в сутки — доступна, только если у препарата задана концентрация и объём («4 ЕД в сутки»);
- е) признак **«без расчёта срока»** (резерв, разовые назначения — только журнал выдач); тогда обе части пустые.

Хотя бы одна часть или признак обязательны.

**Правило выбора нормы:** на день d действует запись с наибольшим `validFrom ≤ d`. Внутри записи **штучная часть приоритетнее МЕ-части**: МЕ-часть используется, только если штучной нет (заказчик: «узкий специалист может написать как угодно; удобно, чтобы считало и так, и так»). Перекрытия записей по датам невозможны: более поздняя запись заменяет предыдущую целиком.

**Пересчёт нормы МЕ → штуки:** расход штук/день = МЕ/сутки ÷ МЕ-в-штуке. Экран показывает человекочитаемый предпросмотр: «4 ЕД/сутки ≈ 1 картридж на 75 дней».

**Статусы назначения:** активно / архив. Архив не показывается в списках, не участвует в уведомлениях и сводной потребности, но сохраняет историю.

### 3.4. Выдача

| Поле | Примечание |
|---|---|
| Назначение | Ссылка |
| Дата | По умолчанию сегодня |
| Количество | Вводится **упаковками и штуками одновременно** (оба поля необязательны, хотя бы одно > 0). Пример: «2 уп + 3 шт» при упаковке №5 = 13 шт. Экран сразу показывает пересчёт: «2 уп × 5 + 3 = 13 шт», для инсулина также «13 карт × 300 МЕ = 3 900 МЕ» |
| Примечание | Необязательно |
| Рецепт | Необязательная привязка |
| Технические поля | id, время создания/изменения, признак удаления |

**Снимок в записи:** `enteredPacks`, `enteredPieces`, `piecesPerPackAtIssue` (штук в упаковке на момент выдачи), `totalPieces = enteredPacks × piecesPerPackAtIssue + enteredPieces`. Расчёты идут только по `totalPieces`. Если позже изменить размер упаковки в справочнике, история и даты не меняются.

Отдельный тип записи — **начальный остаток** (создаётся при быстром старте, п. 10): дата + количество штук + опционально отображаемая дата «обеспечен до» (`shownUntil`). `totalPieces` у него заполнен **всегда**. Если пользователь ввёл только дату «обеспечен до», объём вычисляется один раз при сохранении (п. 4.2, п. 9) и записывается как снимок; `shownUntil` нужен только для показа. В расчёте начальный остаток участвует наравне с выдачей.

| Поле | Примечание |
|---|---|
| Пациент | Ссылка |
| Назначение | Необязательно |
| Серия / номер | Например «75464 № 25 222 011 880» |
| Дата выдачи рецепта | |

| Статус | **выписан / отоварен** хранятся в БД. Статус **«истёк»** вычисляется на лету: «выписан» и срок действия < сегодня |

Привязка выдачи к рецепту предлагает перевести рецепт в «отоварен». Статус можно менять вручную.

## 4. Правило расчёта «обеспечен до»

### 4.1. Соглашения

| Тема | Правило |
|---|---|
| Месяц | фактическое число дней календарного месяца **того дня, для которого считается расход** (28, 29, 30 или 31) |
| Год | фактическое число дней календарного года (365 или 366) |
| Расход в день | N шт/день → N; N шт/мес → N ÷ дней в месяце этого дня; N шт/год → N ÷ дней в году; N шт каждые X дней → N ÷ X; N МЕ/сутки → N ÷ МЕ-в-штуке |
| Арифметика | **только точные дроби** (Rational / BigInteger или общий знаменатель), не double. Случаи 4 и Б1 заканчиваются ровно на нуле, на float они дадут сбой |
| Результат | «обеспечен до» всегда целый день: последний день, на который запаса хватает на **полный** суточный расход |

### 4.2. Алгоритм

1. Берутся все выдачи и начальные остатки назначения, упорядоченные по дате.
2. Запас от выдачи доступен со следующего дня (день выдачи расходным не считается — это соглашение подтверждено практикой заказчика: выдача 06.10.2026 10 штук при норме «1 штука в 7 дней» даёт «обеспечен до 15.12.2026»).
3. Для каждого дня d: расход r(d) по норме, действующей в этот день (п. 3.3, п. 4.3), и по правилам п. 4.1. Если запас ≥ r(d), день покрыт, запас уменьшается на r(d). Иначе это **день дефицита**: запас обнуляется, остаток не уходит в минус.
4. Выдача после перерыва считается с нуля: дефицит прошлого не вычитается.
5. «Обеспечен до» — последний покрытый день непрерывного периода, в который попадает последняя выдача. Если на следующий день после последней выдачи запаса уже не хватает, «обеспечен до» = дата выдачи. Перерывы (дни дефицита) показываются в журнале пометкой «перерыв ДД.ММ–ДД.ММ».
6. Горизонт 5 лет: если запас не исчерпывается, статус «запас есть» без даты.
7. Остаток на дату X = запас после обработки дня X по этому алгоритму (отрицательным не бывает).
8. Выдачи задним числом, правка и удаление допустимы. Расчёт — чистая функция от всей истории (выдачи, остатки, нормы), пересчитывается целиком; кэш допустим только с инвалидацией (п. 11.2).
9. **Начальный остаток** с вводом только даты «обеспечен до»: запас = сумма r(d) **от дня, следующего за датой остатка**, по указанную дату включительно. Если введён и остаток, он приоритетнее. Результат сохраняется в `totalPieces` (п. 3.4) и позже не пересчитывается.

### 4.3. Смена нормы
Норма действует со своей даты (п. 3.3). До неё расход считается по предыдущей записи, после — по новой. Пример из практики заказчика: тест-полоски «6 полосок в день» до 17.06.2026, с 18.06.2026 — «8 полосок в день».

### 4.4. Назначения без срока
Назначения, у которых действующая запись нормы помечена «без расчёта срока» (резерв, «1 флакон в год» и разовые выдачи), не участвуют в расчёте, подсветке и уведомлениях — ведётся только журнал выдач.

### 4.5. Эталонные примеры
Эталонная таблица расчётов для юнит-тестов и приёмки — **Приложение А**. Все семь случаев обязаны сходиться точно. Реализация — по псевдокоду **Приложения Г**.

### 4.6. Исторические даты в плане ДН
«Обеспечен до» у каждой строки истории выдач считается по данным **на момент этой выдачи**: учитываются выдачи до неё включительно и текущая история норм. Так считает заказчик вручную.

## 5. Экраны и пользовательские сценарии

### 5.1. Вкладка «Пациенты» (главная)
- Список пациентов: ФИО, возраст, ближайшая из дат «обеспечен до» по активным назначениям — с цветной подсветкой (п. 7.4). Назначения с неограниченным запасом показываются как «запас > 5 лет» (зелёный).
- Сортировка по умолчанию — по ближайшей дате (самые срочные сверху); переключение на алфавитную.
- Поиск по ФИО.
- Кнопка «+ пациент».

### 5.2. Вкладка «Срочное»
Секции:
1. «Закончилось» — назначения с датой «обеспечен до» раньше сегодня (красный);
2. «Осталось ≤ порога» — от 0 до N дней включительно, N из настроек (по умолчанию 7) — жёлтые;
3. «Рецепты» — статус «выписан», до конца срока действия ≤ порога рецептов из настроек (по умолчанию 14 дней).

Строка: пациент, препарат, дата. Тап по строке лекарства — переход к назначению; по строке рецепта — к рецепту. Назначения с «запасом > 5 лет» и «без расчёта срока» сюда не попадают. Пустое состояние: «Всё под контролем».

### 5.3. Карточка пациента
- Шапка со всеми полями п. 3.1; тап по телефону представителя — звонок (системный набор).
- Список назначений: препарат, норма кратко («8 полосок в день»), «обеспечен до» с цветом, остаток в штуках/упаковках.
- Кнопки: «+ назначение», «Скопировать назначения у другого пациента», «+ выдача» (контекстный быстрый ввод), «План ДН (Word)», «Изменить», «В архив».
- Секция «План наблюдения» — свободный текст (п. 3.1).
- Секция «Рецепты» — все рецепты пациента с превью фото и статусом.

### 5.4. Экран назначения
- Препарат и форма выпуска; текущая норма и «обеспечен до» — крупно, с цветом.
- Остаток: «N шт (M уп)».
- История норм: «с 18.06.2026 — 8 полосок в день», «до 17.06.2026 — 6 полосок в день».
- Журнал выдач: дата, количество с пересчётом, примечание, значок привязанного рецепта, пометки «перерыв».
- Кнопки: «+ выдача», «+ норма», «+ рецепт».

### 5.5. Ввод выдачи (ключевой сценарий — должен быть максимально быстрым)
Не более ~5 касаний: назначение выбрано контекстом → дата (по умолчанию сегодня) → количество (числовая клавиатура, два поля «упаковки» и «штуки», живой пересчёт) → «Сохранить». После сохранения — подтверждение с новой датой: «Обеспечен до 15.12.2026». Примечание и привязка рецепта — по желанию.

### 5.6. Рецепт
Поля п. 3.5. Фото — камера или галерея, несколько снимков. Кнопка «Распознать» (разд. 6). После OCR поля предзаполнены и помечены как требующие проверки; сохранение = подтверждение пользователем.

### 5.7. Настройки
- Уведомления: вкл/выкл; время ежедневной проверки (по умолчанию 08:00); порог дней для лекарств (по умолчанию 7); порог для рецептов (по умолчанию 14).
- Резервные копии: каталог копий, создать полную / быструю копию, восстановить, график (п. 9).
- Блок «Чтобы уведомления приходили надёжно (HyperOS)» — пошаговая инструкция из п. 7.5.
- О приложении.

### 5.8. Пустые состояния
Каждый пустой список сопровождается короткой подсказкой и кнопкой действия («Пациентов пока нет — добавьте первого»).

### 5.9. Правка, удаление и копирование
- **Выдача:** редактируется той же формой, что и ввод; после правки или удаления все даты пересчитываются.
- **Назначение:** «в архив» (рекомендуется) или «удалить» с подтверждением вместе с его выдачами.
- **Препарат:** удаляется, только если по нему нет назначений, иначе только архив. При создании: предупреждение о совпадении названия после нормализации (регистр, лишние пробелы); сохранить всё равно можно.
- **Рецепт:** при удалении привязки выдач обнуляются, фото удаляются.
- **Пациент:** «в архив» (скрыт из списков, сводной и уведомлений, история сохраняется) и «удалить навсегда» (с подтверждением, каскадом удаляет назначения, выдачи, рецепты и фото).
- **Копирование назначений:** кнопка «Скопировать назначения у другого пациента» на карточке пациента; препараты и нормы копируются, `validFrom` = сегодня, выдачи не копируются. Справочник общий, конфликта препаратов нет.
- **Нехватка места** при сохранении фото: понятная ошибка, данные не повреждены (транзакция). Исходный снимок после сжатия не хранится.

## 6. Фото рецептов и распознавание текста

6.1. Фото делается камерой (CameraX) или выбирается из галереи. Перед сохранением — сжатие: длинная сторона ≤ 1600 px, JPEG ≈ 80 % (экономия места). Хранение — в приватном каталоге приложения.

6.2. **OCR — офлайн, Tesseract** (например, Tesseract4Android) с `rus.traineddata` и `eng.traineddata` внутри APK (assets), без загрузки моделей. ML Kit не использовать: кириллицу он не поддерживает. Перед распознаванием — предобработка: оттенки серого, контраст, выравнивание. Выбор между моделями `fast` и `best` — по качеству на тестовых бланках. Если выбран другой движок, требования те же: распознавание без отправки фото наружу.

6.3. Рецепты заказчика **напечатаны** (бланки с QR-кодом и штрихкодом) — печатный текст распознаётся хорошо. Извлекаемые поля: ФИО пациента, дата рождения, серия/номер, дата, наименование препарата/изделия, дозировка, количество, срок действия.

6.4. Результат OCR — **черновик**: поля предзаполняются и помечаются для проверки, пользователь сверяет с фото, правит и сохраняет. Распознанный текст сохраняется вместе с рецептом (для будущего поиска). Рукописные фрагменты распознаются частично — это допустимо, итог всегда подтверждает человек.

## 7. Уведомления и цветовая подсветка

7.1. Ежедневная проверка в заданное время (по умолчанию 08:00). Основной механизм — **AlarmManager с точным временем** (`setExactAndAllowWhileIdle`). В манифесте объявить `USE_EXACT_ALARM` (для установки по APK выдаётся автоматически) и `SCHEDULE_EXACT_ALARM` для Android 12–12L. Агент проверяет на устройстве, что будильник срабатывает; если доступ не выдан, приложение предлагает открыть системные настройки. Запасной вариант — WorkManager с допуском по времени; если проверка пропущена системой, она выполняется при первой возможности. Дополнительно:
- разрешение `POST_NOTIFICATIONS` на Android 13+ (запрос при первом запуске с пояснением);
- `RECEIVE_BOOT_COMPLETED` и перепланирование после перезагрузки и обновления приложения.

7.2. Push-уведомление — **одно сводное в день** при наличии событий: «Заканчивается запас: пациент — препарат, обеспечен до ДД.ММ.ГГГГ» (перечисление). Формат — `InboxStyle`, до 5 строк и «…и ещё N». Порог для лекарств — настраиваемый, по умолчанию 7 дней. Тап по уведомлению открывает вкладку «Срочное».

7.3. Рецепты: событие только для статуса «выписан» с «до конца срока действия ≤ порога» → «Пора выписать новый рецепт: пациент — препарат». По отоваренным и истёкшим не уведомляем.

7.4. Подсветка дат «обеспечен до» (единая во всех списках):
- **красный** — дата строго раньше сегодня (запас закончился);
- **жёлтый** — от 0 до N дней включительно (дата, равная сегодня, жёлтая);
- **зелёный** — позже сегодня + N.

Порог подсветки совпадает с порогом уведомлений.

7.5. **HyperOS/Xiaomi:** без автозапуска фоновые проверки на Xiaomi ненадёжны. В настройках приложения — пошаговая инструкция: «Настройки → Приложения → Med Tracker → Автозапуск: ВКЛ; Экономия заряда: Без ограничений». **Названия пунктов в HyperOS 3 агент сверяет на устройстве и правит текст по факту.** Показ инструкции после установки и по требованию.

## 8. Документы Word

### 8.1. Общие требования
- Формат .docx, редактируемый, кириллица корректна, шрифт Times New Roman, даты в формате ДД.ММ.ГГГГ.
- Генерация локально на устройстве, **напрямую как OOXML** (ZIP: `[Content_Types].xml`, `_rels`, `document.xml`, `styles.xml`). Apache POI и docx4j не использовать, кроме случая явной проверки на устройстве. Сеть не используется.
- Сохранение через системный диалог или кнопку «Поделиться» (почта, мессенджеры).
- Имена файлов: «План_ДН_Фамилия_И.docx», «Сводная_потребность_ММ.ГГГГ.docx».

### 8.2. Документ «План диспансерного наблюдения» (по пациенту)
Структура повторяет текущие файлы заказчика (пациент должен узнать свой документ):

1. Заголовок: «План диспансерного наблюдения» (+ диагноз, если заполнен).
2. Шапка: ФИО; дата рождения; адрес; школа/класс/детсад; начало заболевания; льгота и с какого числа (региональная/федеральная); представитель с телефонами; лечащий врач.
3. Раздел «ПОТРЕБНОСТЬ» — по каждому активному назначению:
   - препарат и форма выпуска;
   - нормы с периодами действия: «фиасп — 10 картриджей в месяц»; «тест-полоски: 6 полосок в день до 17.06.2026; с 18.06.2026 — 8 полосок в день»;
   - история выдач построчно: «Выдано 08.09.2025 — 6 уп по 5 шт — обеспечен до 14.02.2026» (даты считаются по п. 4.6);
   - назначениям «без срока» — только история выдач, без даты.
4. Текущий статус по каждому назначению — «Обеспечен до ДД.ММ.ГГГГ» (выделить жирным); при неограниченном запасе — «запас достаточен».
5. Раздел «План наблюдения» — свободный текст заметок пациента.

### 8.3. Документ «Сводная потребность» (по всем пациентам)
Параметр — период (по умолчанию следующий календарный месяц). Таблица по всем препаратам активных назначений (архивные назначения и архивные пациенты не учитываются), сортировка по названию:

| № | Препарат и форма выпуска | Требуется на период | Осталось на начало периода | Докупить | У кого заканчивается и когда |
|---|---|---|---|---|---|
| 1 | Тест-полоски OneTouch Select Plus, уп. по 50 шт | 900 шт (18 уп) | 250 шт | 650 шт (13 уп) | Сарапулов К. — 02.12.2026; Тестов Т. — 09.12.2026 |

- «Требуется на период» для месяца M — сумма по пациентам: N шт/день → N × дней в M; N шт/мес → N; N шт/год → N × дней в M ÷ дней в году; N шт каждые X дней → N × дней в M ÷ X; нормы МЕ пересчитываются в штуки по п. 3.3. Округление вверх до целой штуки после суммирования по пациентам.
- «Осталось на начало периода» = суммарный остаток всех пациентов по препарату на 1-е число месяца M по п. 4.2 (пункт 7).
- «Докупить» = максимум из 0 и («Требуется» − «Осталось»).
- Параллельно со штуками показывать упаковки, если у препарата задан размер упаковки.
- «Запас > 5 лет» в столбец «У кого заканчивается и когда» не попадает.

## 9. Резервное копирование («умное сохранение»)

Требование заказчика: хранить одну полную копию и применять к ней только изменения.

9.1. **Каталог копий** выбирается один раз через **Storage Access Framework** (`ACTION_OPEN_DOCUMENT_TREE`), доступ сохраняется через `takePersistableUriPermission`. Разрешения на хранилище не запрашиваются. По умолчанию предлагается `Documents/MedTracker`. Если доступ утрачен (переустановка, отзыв), приложение просит выбрать папку заново; плановые копии пишутся в этот же каталог. **Полная копия** — один файл-контейнер (ZIP): база целиком в человекочитаемом JSON + все фото. Имя: `MedTracker_полная_ГГГГММДД_ЧЧММ.mtbackup`.

9.2. **Быстрая копия (изменения)** — только записи, изменённые с момента последней полной копии, и новые фото: `MedTracker_быстрая_ГГГГММДД_ЧЧММ.mtdelta`. Хранится рядом с полной.

9.3. **Восстановление:** выбор полной копии и последующих быстрых (по порядку дат) → предпросмотр (дата копии, число пациентов/выдач/фото) → подтверждение → замена данных. Перед заменой автоматически создаётся страховая полная копия текущего состояния. Если страховую копию создать не удалось (нет места, нет доступа), восстановление отменяется, данные не затрагиваются.

9.4. **График:** быстрая копия — еженедельно, полная — ежемесячно (время задаётся в настройках). Напоминание-пуш, если копий не было более 7 дней.

9.5. **Целостность:** контрольная сумма в манифесте контейнера; при повреждении — понятная ошибка, текущие данные приложения не затрагиваются.

9.6. Формат контейнера и JSON-схема документируются в README, чтобы базу можно было прочитать без приложения.

9.7. **Манифест** содержит: `schemaVersion` БД, версию приложения, `fullId` (UUID полной копии), для быстрой копии `parentFullId` и порядковый номер, число записей по типам, контрольные суммы файлов.

9.8. **Удаления** фиксируются в быстрой копии tombstone-записями (id, тип, время удаления). Без них восстановление воскресит удалённое.

9.9. Быстрая копия применима только к своей полной (`parentFullId`). Новая полная копия начинает новую цепочку.

9.10. **Хранение:** приложение хранит последние 3 полные копии с их цепочками. Старые удаляются **только вручную**: после новой полной копии приложение предлагает удалить лишние (с подтверждением).

9.11. При восстановлении копии старой схемы выполняется миграция по `schemaVersion`; копия из более новой версии приложения отклоняется с понятным сообщением.

9.12. В README одной строкой: копии не шифруются, храните их в надёжном месте.

## 10. Первый запуск

1. Экран приветствия (2–3 предложения о приложении) → «Начать».
2. Мастер добавления первого пациента: поля п. 3.1.
3. Добавление назначения: выбор/создание препарата, форма выпуска, норма (любой вид из п. 3.3).
4. Блок «Уже обеспечен» — для быстрого старта без истории: пользователь вводит текущую дату «обеспечен до» и, при желании, остаток в штуках. Приложение сохраняет это как **начальный остаток** (п. 3.4) и использует в расчётах наравне с выдачами.
5. Повтор по всем пациентам и назначениям. Полная история выдач ведётся с момента установки.
6. Настройки работают со значениями по умолчанию, менять не обязательно.
7. Архив и удаление пациента — п. 5.9.
8. Быстрое наполнение: «Скопировать назначения у другого пациента» — п. 5.9.

## 11. Нефункциональные требования

11.1. **Офлайн и приватность:** разрешение `INTERNET` не запрашивать; данные пациентов не попадают в логи, отчёты об ошибках и внешние сервисы; `android:allowBackup=false` (копии пользователь делает сам). Допустимые разрешения: `CAMERA`, `POST_NOTIFICATIONS`, `USE_EXACT_ALARM`, `SCHEDULE_EXACT_ALARM`, `RECEIVE_BOOT_COMPLETED`.

11.2. **Производительность** на целевом устройстве:
- холодный старт ≤ 2 с;
- список 100 пациентов и 1000 выдач прокручивается без пропуска кадров;
- расчёт идёт в фоне, результаты кэшируются в БД и инвалидируются при изменении выдач или норм этого назначения; открытие списка ≤ 200 мс с кэша, полный пересчёт всех назначений ≤ 1,5 с.

11.3. **Надёжность:** изменения базы — транзакционно; любая ошибка сопровождается понятным сообщением на русском без краха приложения; штатные операции не приводят к потере данных.

11.4. **Интерфейс:** русский язык; крупные элементы; поддержка системной тёмной темы; удобство на экранах 6–6.7″; ориентация экрана только портретная.

11.5. **Совместимость:** целевое устройство — Xiaomi 13 Lite, HyperOS 3, Android 15. Совместимость: Android 8.0–15 (minSdk 26, targetSdk 35).

## 13. План разработки и критерии приёмки

### 13.1. Рекомендуемый стек
Kotlin + Jetpack Compose (Material 3), Room, AlarmManager и WorkManager, CameraX, Tesseract (rus + eng). Для .docx — прямая сборка OOXML через ZIP. Агент вправе заменить компоненты с обоснованием, сохранив все требования (офлайн, OCR на устройстве, генерация .docx, фоновые уведомления).

### 13.2. Этапы (каждый этап заканчивается устанавливаемым билдом)
1. Каркас проекта, модель данных, пациенты.
2. Назначения и нормы + расчёт «обеспечен до» (юнит-тесты по Приложению А).
3. Выдачи, подсветка, вкладка «Срочное».
4. Рецепты: фото + OCR.
5. Уведомления.
6. Документы Word (начинается с пробного документа, который открывается в Word и WPS).
7. Резервные копии.
8. Полировка, CI, релиз `v1.0.0`.

### 13.3. Чек-лист приёмки
1. Пациент создаётся со всеми полями п. 3.1; тап по телефону — звонок.
2. Создаются все виды норм; изменение нормы создаёт новую запись, история сохраняется.
3. Расчёт «обеспечен до» совпадает со **всеми семью** строками Приложения А.
4. Ввод выдачи укладывается в ~5 касаний; пересчёт упаковки/штуки/МЕ верен; после сохранения дата обновляется.
5. Подсветка красный/жёлтый/зелёный соответствует порогам п. 7.4.
6. Сводное push-уведомление приходит в заданное время при наличии событий (на Xiaomi — после настройки автозапуска из п. 7.5).
7. На 10 вымышленных тестовых бланках правильно предзаполняется ≥ 80 % полей; ручные исправления сохраняются.
8. Оба документа генерируются и открываются в Word и WPS без ошибок, кириллица и таблицы корректны.

## Приложение Г. Псевдокод расчёта

```
supplyEnd(p):
  events = выдачи и начальные остатки по дате    # totalPieces заполнен всегда
  if пусто: return NONE
  last = events.last.date; stock = 0; covered = null
  for d in (events.first.date+1 .. last + 5 лет):
     stock += sum(totalPieces у событий с date == d-1)
     r = rate(d)                  # п. 4.1; норма = запись с max validFrom ≤ d
     if stock >= r: stock -= r; covered = d
     else:          stock = 0; if d > last: break   # дефицит после последней выдачи
  else: return UNLIMITED          # дошли до горизонта: «запас есть»
  return max(covered ?? last, last)
```

Функция `rate(d)` берёт запись нормы с наибольшим `validFrom ≤ d`: если у неё есть штучная часть, считает по ней (п. 4.1), иначе по МЕ-части, иначе (`noCalc`) расчёт для назначения пропускается (п. 4.4).
