## 2. Ф1 — Скан-поток «Рецепт» и просмотр фото

**Текущее состояние** (project.md §6 п.8): вкладка «Рецепт» (`RxScanScreen`): скан бланка → OCR автоматически → проверка полей → автоподбор пациента по ФИО (создание нового на месте) и назначения по препарату (`ocr/TextMatch.kt`) → сохранение рецепта, кнопка «Выдать сейчас». Фото — в `filesDir/photos` через `PhotoStore`.

### Требования

- **Ф1.1. Просмотр фото.** После добавления снимка (камера или галерея) в формах `RxEdit` и `RxScan` показывается миниатюра; тап открывает полноэкранный просмотр с масштабированием жестами (pinch-zoom, перетаскивание). Просмотр работает и **после сохранения рецепта** — из карточки рецепта / экрана назначения / вкладки «Рецепт» по сохранённому пути. Если файла нет (перемещён/удалён) — вежливое сообщение, без краша.
- **Ф1.2. Повторное распознавание из просмотра.** В полноэкранном просмотре кнопка «Распознать заново»: запускает OCR по этому фото; если просмотр открыт из открытой формы — заполнить поля формы; если из карточки сохранённого рецепта — показать распознанный текст диалогом с возможностью скопировать (в поля переносится вручную). Ошибки OCR — через `OcrEngine.friendlyError()` (как в v1.1.1), перехват `Throwable`, не крашить.
- **Ф1.3. Автозаполнение скан-потока.** После OCR во вкладке «Рецепт» заполняются все поля: ФИО пациента, дата рождения, МКБ, серия/№, дата выдачи и срок рецепта, наименование выдаваемой позиции (препарат/устройство), дозировка/форма. Автоподбор пациента — как есть (с созданием нового на месте). Автоподбор назначения — по распознанному наименованию с учётом устройств (Ф4.2); при неоднозначности — список кандидатов на ручной выбор. Если позиции нет в справочнике — диалог быстрого создания «на месте» (по аналогии с пациентом) с выбором вида «препарат/устройство».
- **Ф1.4. Выдача с датой рецепта.** Существующая кнопка «Выдать сейчас» **заменяется** кнопкой «Выдать»: она сохраняет рецепт (если ещё не сохранён) и открывает обычную `IssueForm`, где **дата по умолчанию = распознанная/введённая дата выдачи рецепта** (не сегодняшняя), количество — как в прежней «Выдать сейчас». Выдача создаётся только после подтверждения пользователем в форме (автосохранения нет). После сохранения «обеспечен до» пересчитывается через `CalcService` (проверить на этом сценарии).
- **Ф1.5. Будущая дата выдачи** блокируется с объяснением (по образцу блокировки будущей даты рождения из v1.0.1).
- **Ф1.6. FileProvider.** Любой новый каталог/кэш, используемый просмотром или повторным OCR, добавить в `res/xml/file_paths.xml`.

### Приёмка Ф1
1. Отсканировать бланк → поля заполнены → пациент и назначение подобраны → «Выдать» открыла форму с датой рецепта → подтверждение → в журнале выдача этой датой, «обеспечен до» пересчитан.
2. Миниатюра и полноэкранный просмотр работают до и после сохранения; зум плавный; «Распознать заново» не крашит при нативном сбое.

## 3. Ф2 — Резервная схема лечения

Заказчик: «скрой полностью в срочном, во вкладке пациент сделай отдельную строчку для резервного препарата, там так же делается расчёт, но не приходят уведомления».

### Требования

- **Ф2.1.** У `Prescription` новый признак `isReserve` (Boolean, по умолчанию `false`). Редактируется в `PrescriptionEdit` переключателем «Резервная схема»; в экране назначения и карточке пациента — чип «Резерв».
- **Ф2.2.** Миграция БД — единая v2 → v3 (§9).
- **Ф2.3. Вкладка «Срочное»:** назначения с `isReserve` исключаются **полностью** — из основного списка, из секции «В ожидании поступления» и из формирования `UrgentItem` (фильтрация на уровне `Repo`/DAO-запросов; движок расчёта не трогать).
- **Ф2.4. Карточка пациента:** отдельная секция **«Резервные препараты»** — по строке на назначение: позиция, «обеспечен до» с обычной подсветкой (красный/жёлтый/зелёный), чип «Резерв». Расчёт ведётся как у обычных назначений.
- **Ф2.5. Уведомления:** резервные назначения не попадают в ежедневную сводку (`notify/Notify.kt`, `DailyCheck`) и не порождают иных уведомлений.
- **Ф2.6.** Кнопка «В ожидании поступления» у закончившегося резервного препарата доступна в секции резервных (в карточке пациента); статус снимается выдачей как обычно, но в «Срочное» резервный препарат при этом не возвращается.
- **Ф2.7. Документы Word (решение по умолчанию, подтвердить с заказчиком):**
  - «Сводная потребность» (п. 8.3) — резервные назначения **исключаются** (документ планирует закупку по основным схемам);
  - «План диспансерного наблюдения» (п. 8.2) — резервные **включаются** с пометкой «(резерв)» в строке позиции.
  Реализовать флагом на уровне построения данных документа, сами генераторы `DocxBuilder` не переписывать.

### Приёмка Ф2
3. Назначение помечено «Резервная схема» → исчезло из «Срочного» (в т.ч. когда запас закончился) → видно в карточке пациента в секции «Резервные» с корректным «обеспечен до» → ежедневная сводка о нём не упоминает → обычное назначение рядом ведёт себя по-старому (регресс) → в «Сводной потребности» резерва нет, в «Плане ДН» он с пометкой.

## 4. Ф3 — Вкладка «Анализы» (диабет)

Заказчик: «добавить для диабетиков вкладку анализы — гликированный гемоглобин, возможность редактирования, оповещение в них; сдаётся 1 раз в 3 месяца; и добавить возможность создать свои анализы». Уточнения: напоминание — **отдельным уведомлением**; диабет — **МКБ E10–E11 плюс пометка вручную**; **цветовой ориентир значения не нужен**; периодичность своих анализов — настраиваемая.

### Требования

- **Ф3.1. Навигация:** нижняя вкладка «Анализы» **между «Пациенты» и «Срочное»** (итого: Пациенты, Анализы, Срочное, Рецепт, Настройки). Подписи короткие; проверить, что 5 вкладок не сжимаются на узких экранах.
- **Ф3.2. Вид анализа (`AnalysisType`):**
  - встроенный «Гликированный гемоглобин (HbA1c)»: единица «%», период 3 месяца, `isBuiltIn = true`; **хранится строкой в таблице `analysis_types`**, засевается в миграции v2→v3 и при создании БД с нуля (`RoomDatabase.Callback.onCreate`); удалять нельзя, период править можно;
  - пользовательские виды: название (обязательно), единица измерения (текст, необязательно), периодичность в месяцах (целое ≥ 1; 1 = раз в месяц).
  Создание/редактирование видов — из вкладки «Анализы».
- **Ф3.3. Запись анализа (`AnalysisRecord`):** пациент, вид, дата, значение (число), комментарий (необязательно). Ввод/редактирование/удаление. Даты — через `DatePickerField` (календарь, ручной ввод убран — правило v1.0.1); будущая дата блокируется. Список — свежие сверху. При удалении вида анализа с записями — подтверждение, записи удаляются каскадно (кроме встроенного, который удалять нельзя).
- **Ф3.4. Экран вкладки «Анализы»:** список пациентов-диабетиков (пометка вручную ИЛИ МКБ начинается с E10/E11, с учётом нормализации кириллических двойников Е10→E10). По каждому: вид анализа, последний результат с датой и статус срока:
  - «в срок» — до даты следующей сдачи;
  - «пора сдавать (просрочено на N дн.)» — следующая сдача (= дата последней записи + период в месяцах, `LocalDate.plusMonths`) наступила или прошла (в день срока — «пора сдавать», 0 дн.);
  - «нет данных» — записей этого вида у пациента нет.
  Отдельная секция/фильтр «Пора сдавать» (включает «нет данных»). Быстрое действие «Отметить сдачу» — сразу форма новой записи.
- **Ф3.5. Карточка пациента:** секция «Анализы» — записи всех видов с кнопкой добавления; доступна любому пациенту (не только диабетику), чтобы работали «свои анализы» для остальных.
- **Ф3.6. Пометка «Диабет»** в `PatientEdit` (переключатель); она ИЛИ МКБ E10/E11 делает пациента «диабетиком» для этой фичи.
- **Ф3.7. Напоминания — отдельные уведомления** (не в ежедневной сводке), отдельный канал уведомлений «Анализы», заголовок «Пора сдавать анализ», текст «ФИО — Гликированный гемоглобин (HbA1c), последний 12.08». Правила (однозначные):
  1. Пара (пациент, вид анализа) **с хотя бы одной записью**: когда срок сдачи наступил или прошёл — напоминание **раз в день**, пока не добавлена новая запись.
  2. Пациент-диабетик **без единой записи** HbA1c: напоминание «нет данных» **не чаще раза в 7 дней** (дата последнего такого напоминания по пациенту хранится в `SettingsStore`).
  3. Для остальных пациентов (не диабетиков) и для пользовательских видов без записей — напоминаний нет (виден статус только в карточке).
  4. Если у пациента сразу несколько просроченных видов — **одно уведомление на пациента в день** со списком видов в тексте (InboxStyle).
  5. Напоминания приходят в настраиваемое время (Ф5.1; по умолчанию 08:00), механизм — `AlarmScheduler` + ежедневная проверка в `CheckWorker`/`DailyCheck`.
  6. Расписание анализов и ежедневной сводки — **два независимых будильника** (разные request code/действия). Оба перепланируются: при изменении времени в настройках, после `BOOT_COMPLETED`, после восстановления из резервной копии, после обновления приложения (если `AlarmScheduler` это уже делает для сводки — распространить на второй). Дублирования будильников быть не должно (идемпотентное планирование: cancel → set).
- **Ф3.8.** Цветовых ориентиров по значению анализа **не делать** (решение заказчика).

### Приёмка Ф3
4. Пациенту с E10 внесён HbA1c → дата последнего сдвинута назад на 3+ месяца → в назначенное время приходит отдельное уведомление с ФИО (проверка на устройстве — заказчик) → запись отредактирована/удалена корректно.
5. Создан свой анализ «раз в месяц» → срок считается от последней записи + 1 месяц; статус в карточке корректен.
5а. Диабетик без записей: статус «нет данных», напоминание не чаще раза в 7 дней (проверяется юнит-тестом логики; на устройстве — заказчик).

## 5. Ф4 — Препараты/устройства и врач в рецепте

Заказчик: «С рецепта должны распознаваться выдаваемый препарат/устройство и т.д., день выдачи рецепта совпадает с днём выдачи препарата/устройства, ФИО доктор выбирает сам».

### Требования

- **Ф4.1. Справочник позиций:** у `Drug` новое поле вида позиции `kind`: «препарат» (по умолчанию) | «устройство». Устройства (тест-полоски, глюкометр, шприц-ручки и т.п.) заводятся в общий справочник; штучный расчёт работает как есть (для устройств МЕ-часть нормы обычно не задаётся). Вид показывается в диалоге позиции, списках и при подборе из OCR. Проверить, что устройства корректно отображаются в «Сводной потребности» и «Плане ДН» (штучные формы слова — `pieceNounForms`).
- **Ф4.2. Подбор из рецепта:** `ocr/TextMatch.kt` подбирает назначения и по устройствам; при нескольких кандидатах — список для ручного выбора. `TextMatchTest` расширить вымышленными названиями (в т.ч. устройства).

## 6. Ф5 — Настройки

- **Ф5.1. Время уведомлений.** В настройках задаётся время ежедневной сводки (сейчас жёстко 08:00) и время напоминаний об анализах (по умолчанию 08:00). Ввод — Material 3 `TimePicker` (не ручной текст). Хранение в `SettingsStore` (DataStore). При изменении — немедленное перепланирование соответствующего будильника (идемпотентно, см. Ф3.7 п.6).

- **Ф5.3. Настройки в резервной копии.**
  1. Агент **сначала выясняет**, входят ли настройки (пороги, время уведомлений, прочее из `SettingsStore`) в `manifest.json/db.json` сейчас.

9. Настройки на узком экране: элементы переносятся по строкам, ничего не сжато и не обрезано.

### Миграция Room v2 → v3 (schemaVersion = 3), неразрушающе

**Правило:** агент сначала читает `data/db/Entities.kt` и **добавляет только те колонки, которых там ещё нет** (иначе `ALTER TABLE ADD COLUMN` упадёт на дубликате). Список целевых изменений:

2. Напоминания об анализах — отдельные уведомления, отдельный канал, время настраиваемое, по умолчанию 08:00; правила частоты — Ф3.7 (раз в день при просрочке с записями; не чаще раза в 7 дней при отсутствии записей у диабетика; одно уведомление на пациента).
3. «Диабетик» = пометка вручную ИЛИ МКБ E10/E11.
4. Врач — ручной ввод/выбор из ранее введённых; OCR не используется.
5. Устройства — в общем справочнике с видом «устройство», штучный расчёт как у препаратов. **Подтверждено заказчиком 01.11.2026.**
6. Выдача из скан-потока открывает форму с датой рецепта и создаётся только по подтверждению пользователя; кнопка «Выдать сейчас» заменяется кнопкой «Выдать».
7. Повторный OCR из полноэкранного просмотра — дополнение по итогам беседы (недорогое и полезное); можно исключить.
8. Вкладка «Анализы» показывает пациентов с диабетом; секция «Анализы» в карточке доступна любому пациенту.
9. Резервные назначения: исключены из «Сводной потребности», включены в «План ДН» с пометкой «(резерв)». **Требует подтверждения заказчика.**
10. Встроенный HbA1c хранится строкой в `analysis_types` (`isBuiltIn`), засевается миграцией и `onCreate`.
11. В резервную копию входят настройки (время уведомлений, пороги, размер шрифта); не входят путь каталога копий, `lastFullId`, служебные даты напоминаний.
12. Ф6: количество по умолчанию — штучная норма за период, иначе последняя выдача; дата — сегодня.
13. Ф8: порог 14 дней, настраивается, 0 = не напоминать; строкой в ежедневной сводке, не отдельным уведомлением.
14. Ф9: период «с/по» двумя календарями; начальные остатки — отдельной пометкой в строке.
15. Ф10: предпросмотр — только чтение движка; при дефиците — цветовая подсветка.
16. Ф11: два размера шрифта (обычный/крупный), для всего приложения.
17. Ф12: приоритет низкий; допустимо исключить без согласования.
