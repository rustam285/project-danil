## 1. Суть фичи и текущее состояние

**Заказчик:** при сканировании рецепта — выдавать препарат/устройство сразу со экрана проверки полей; дата выдачи = дата выдачи рецепта; количество берётся из рецепта («Количество единиц» × «№» из строки Dtd).

**Что уже есть (v1.3.0, не переделывать):**
- вкладка «Рецепт» (`ui/screens/RxScanScreen.kt`): скан → OCR → проверка полей → автоподбор пациента/назначения → «Сохранить рецепт»; в диалоге после сохранения — кнопка «Выдать», открывающая полную форму выдачи с датой рецепта (Ф1.4);
- `Issue.rxId` (связь выдачи с рецептом, индекс есть), `IssueDao.forRx()` — `data/db/Daos.kt`;
- авто-перевод рецепта в «отоварен» при привязке выдачи в форме выдачи — `IssueFormScreen.kt` (блок «Перевод рецепта в "отоварен" при привязке (п. 3.5)»);
- предпросмотр «обеспечен до» на чтение — `calc/IssuePreview.kt` (Ф10);
- `Repo.saveIssue(existing, prescriptionId, date, packs, pieces, note, rxId, piecesPerPack)` — `data/Repo.kt`; снимает «В ожидании поступления».

**Что добавляет Ф13:** вторая кнопка «Сохранить и выдать» с количеством из рецепта, диалогом подтверждения (блокировки/предупреждения/предпросмотр) и возможностью отмены; распознавание новых полей бланка; дубль-проверка по серии и номеру.

**Известные расхождения черновика беседы с кодом (уже учтены в этом ТЗ, заново не открывать):**
- `Repo.saveRx` не существует — рецепт сохраняется в `RxScanViewModel.save()`; новый метод пишем рядом в `Repo`;
- Rooms KTX уже подключён (`room-ktx` 2.6.1), `db.withTransaction` уже используется в `BackupManager`;

## 2. Ф13.1 — Зафиксированные решения (кратко, детали в разделах ниже)

1. **Две кнопки** на экране проверки полей: «Сохранить рецепт» (как сейчас) и «Сохранить и выдать». Автоматической выдачи без подтверждения нет.
2. **Штуки = «Количество единиц» × «№»** из строки Dtd. При совпадении «№» с упаковкой справочника — в журнал «P уп × K»; при несовпадении — штуками с предупреждением (§5).
3. **Назначения нет — создаётся на месте**: позиция из справочника или новая (предзаполненная из OCR), затем обязательная форма нормы; выдача — после сохранения нормы.
4. **Дубли** ловятся по серии и номеру (без пробелов): есть выдача по этому рецепту — блокировка; рецепт сохранён без выдачи — переиспользуется, не создаётся заново (§6).
5. **Отсроченное обеспечение**: выдача датой рецепта, предупреждение в диалоге; определяется по «ОТСРОЧ» в тексте OCR + ручной переключатель.
6. **Просроченный рецепт** — предупреждение, выдача разрешена; **будущая дата рецепта — блок** (как Ф1.5).
7. **Норма автоматически не создаётся и не меняется.** Для нового назначения — форма нормы с `validFrom` = дата рецепта (редактируемая), распознанная Signa — подсказкой над формой.
8. **Выдача по назначению позже даты рецепта** — предупреждение без блокировки.
9. **Статус рецепта после выдачи — «отоварен» (REDEEMED)**, как в форме выдачи (п. 3.5 ТЗ 1.1). «Отменить выдачу» возвращает «выписан», если по рецепту не осталось других выдач (§7).
10. Дубль-проверка единая для всех путей: старый путь «Выдать» тоже передаёт `rxId` (§6.3); при пустых серии/номере проверка не выполняется (§6.2).

Правила распознавания (готовые regex, **исполнить как есть** — учтена грабля project.md §7 про квантификаторы после кириллицы и реальная метка «Выписано Вр.»):

```kotlin
val unitsCount = Regex("""[Кк]оличеств[оа]\s+единиц[^\d\n]{0,6}(\d{1,4})""")
    .find(text)?.groupValues?.get(1)?.toIntOrNull()

// Dtd. / D.t.d. — ищем строку с меткой, затем «№N» в ней или в следующей строке
val dtdMark = Regex("""D[.\s]*t[.\s]*d""", RegexOption.IGNORE_CASE)
val packSize = run {
    val i = lines.indexOfFirst { dtdMark.containsMatchIn(it) }
    if (i < 0) null else (i..minOf(i + 1, lines.lastIndex)).firstNotNullOfOrNull { idx ->
        Regex("""(?<![A-Za-zА-Яа-я])[№Nn]\s*(\d{1,4})""").find(lines[idx])
            ?.groupValues?.get(1)?.toIntOrNull()
    }
}

val signa = Regex("""Signa\s*[:.]?\s*(.+)""", RegexOption.IGNORE_CASE)
    .find(text)?.groupValues?.get(1)?.trim()

// значение — сначала на той же строке после метки, затем на следующей строке
fun labelValue(labelRe: Regex): String? {
    for (line in lines) {
        val m = labelRe.find(line) ?: continue
        val same = line.substring(m.range.last + 1).trim(':', '.', ' ', '|').trim()
        if (same.length >= 3) return same
    }
    val i = lines.indexOfFirst { labelRe.containsMatchIn(it) }
    return if (i in 0 until lines.lastIndex) lines[i + 1].trim().takeIf { it.length >= 3 } else null
}
val rpName = labelValue(Regex("""[Вв]ыписан[оа]\s+(?:Rp|Вр)"""))
val formName = labelValue(Regex("""[Фф]орм[аы]\s+выпуск[аы]"""))

val deferred = text.uppercase().contains("ОТСРОЧ")
```

Пояснения и границы:
- `lines` — уже существующий в `parse()` список непустых обрезанных строк.
- Если OCR не нашёл поле — `null`, поле заполняется вручную; **молча угадывать нельзя**.
- `packSize` не найден (например, «Дозировка Dtd.» без №) — это нормальный случай: блокировка в плане выдачи (§5) предложит ввести вручную.
- Учесть известный край: если строки склеились и в окно поиска `packSize` попал номер рецепта («№ 26 222…») — regex возьмёт первые 1–4 цифры; защита — ручная сверка в диалоге подтверждения (§8), ничего дополнительно не делать.
- Названия в «Rp.» бывают общими («Test-poloski», «Medical device»), настоящее название — в корешке; поэтому подбор позиции использует весь текст рецепта (§4), а не только `rpName`.

/** Доля токенов названия, найденных в тексте рецепта (0..100). */
fun coverage(text: String, name: String): Int {
    val nt = tokens(name); if (nt.isEmpty()) return 0
    val nn = normalize(name)
    if (nn.isNotEmpty() && normalize(text).contains(nn)) return 100
    val tt = tokens(text)
    return nt.count { it in tt } * 100 / nt.size
}

## 5. Ф13.4 — Чистая логика плана выдачи (`data/RxIssuePlan.kt`)

Новый файл, только чистые функции и данные (покрывается юнит-тестами, без Android):

```kotlin
object RxIssuePlan {
    data class Input(
        val units: Int?, val packSize: Int?, val drugPiecesPerPack: Int,
        val rxDate: LocalDate?, val today: LocalDate, val validUntil: LocalDate?,
        val deferred: Boolean, val existingIssueDate: LocalDate?, val laterIssueDate: LocalDate?,
    )
    data class Plan(
        val packs: Int, val pieces: Int, val total: Int,
        val blocks: List<String>, val warnings: List<String>,
    )

    fun build(i: Input): Plan {
        val blocks = mutableListOf<String>(); val warn = mutableListOf<String>()
        val u = i.units?.takeIf { it > 0 }
        val p = i.packSize?.takeIf { it > 0 }
        if (u == null) blocks += "Укажите «Количество единиц»"
        if (p == null) blocks += "Укажите размер упаковки (№)"
        if (i.rxDate == null) blocks += "Укажите дату рецепта"
        else if (i.rxDate.isAfter(i.today)) blocks += "Дата рецепта в будущем"
        i.existingIssueDate?.let { blocks += "По этому рецепту уже есть выдача от ${Dates.formatRu(it)}" }
        val total = if (u != null && p != null) u * p else 0
        var packs = 0; var pieces = 0
        if (u != null && p != null) {
            if (p == i.drugPiecesPerPack) packs = u
            else {
                pieces = total
                warn += "Упаковка в справочнике (${i.drugPiecesPerPack}) не равна рецепту (№$p): выдача запишется штуками ($total шт)"
            }
        }
        if (i.deferred) warn += "Рецепт поставлен на отсроченное обеспечение: выдача записывается датой рецепта"
        i.validUntil?.takeIf { it.isBefore(i.today) }?.let { warn += "Срок действия рецепта истёк ${Dates.formatRu(it)}" }
        i.laterIssueDate?.let { warn += "По назначению уже есть выдача от ${Dates.formatRu(it)} (позже даты рецепта): «обеспечен до» пересчитается с её учётом" }
        return Plan(packs, pieces, total, blocks, warn)
    }
}
```

Уточнения:
- `validUntil` вызывающая сторона вычисляет как `rx.validUntil ?: (issueDate + validDays)` (в `ScanState` поля `validUntil` нет — вычислить во ViewModel).
- `existingIssueDate` — дата выдачи, связанной с этим рецептом (`issues.rxId`, §6); `laterIssueDate` — самая ранняя выдача назначения с датой строго позже даты рецепта.
- `blocks` непустые → кнопка выдачи в диалоге недоступна, только текст блокировок; `warnings` показываются, выдача разрешена.

## 6. Ф13.5 — Дубль-проверка и переиспользование рецепта

### 6.1. Запрос DAO

В `RxDao` добавить:

```kotlin
@Query("SELECT * FROM rxs WHERE series = :s AND REPLACE(number, ' ', '') = :n")
suspend fun bySeriesNumber(s: String, n: String): List<Rx>
```

**Вызывающая сторона обязана нормализовать аргументы в Kotlin** (REPLACE применяется только к колонке): `s = series.trim()`, `n = number.replace(Regex("[\\s-]"), "").trim()`.

### 6.2. Guard от ложных срабатываний

- Если серия **или** номер пусты/blank — дубль-проверка **не выполняется** (запрос по пустым строкам заматчит все рецепты без серии/номера). В этом случае в диалоге подтверждения показывать предупреждение: «Серия и номер не заполнены — повторную выдачу по этому бланку не удастся распознать».
- Если найденный рецепт-дубль привязан к **другому пациенту** — предупреждение без блокировки («Рецепт с этой серией/номером уже сохранён у пациента X»).

### 6.3. Дыра старого пути «Выдать» (обязательная правка)

Сейчас `RxScanScreen` после «Сохранить рецепт» открывает форму выдачи без связи с рецептом (`Routes.issueEdit(pid, null, rxDate)`; маршруту неоткуда взять `rxId`), и выдача остаётся с `rxId = null` — дубль-проверка её не видит. Исправить:
- маршрут `issueEdit` расширяется необязательным параметром `rxId` (по образцу `issueId`/`date`, `-1L` как «нет»);
- `RxScanScreen` в кнопке «Выдать» передаёт `savedRxId`;
- `IssueFormScreen` при создании новой выдачи предвыбирает чип рецепта по переданному `rxId` (существующая логика авто-«отоварен» при этом сработает как есть).

### 6.4. Переиспользование

Если рецепт с такой серией/номером уже сохранён и **не имеет выдач** (`IssueDao.forRx(id)` пуст) — он переиспользуется: его поля обновляются (в т.ч. `prescriptionId`), новый `Rx` не вставляется. Если имеет — блокировка из §5.

## 7. Ф13.6 — Транзакция выдачи и отмена (`Repo`)

```kotlin
suspend fun issueFromRx(rx: Rx, prescriptionId: Long, plan: RxIssuePlan.Plan, piecesPerPack: Int): Issue =
    db.withTransaction {
        val t = now()
        val date = requireNotNull(rx.issueDate) { "Дата рецепта не заполнена" } // без !!
        val rxId = if (rx.id == 0L) rxDao.insert(rx.copy(prescriptionId = prescriptionId))
                   else rx.id.also { rxDao.update(rx.copy(prescriptionId = prescriptionId, updatedAt = t)) }
        val issue = saveIssue(
            existing = null, prescriptionId = prescriptionId, date = date,
            packs = plan.packs, pieces = plan.pieces,
            note = "Рецепт ${rx.series} № ${rx.number}".takeIf { rx.series.isNotBlank() || rx.number.isNotBlank() },
            rxId = rxId, piecesPerPack = piecesPerPack,
        )
        // п. 3.5 ТЗ 1.1: выдача по рецепту — «отоварен» (решение заказчика 01.11.2026)
        rxDao.byId(rxId)?.let { if (it.status != "REDEEMED") rxDao.update(it.copy(status = "REDEEMED", updatedAt = t)) }
        issue
    }
```

- Переиспользование из §6.4 решает вызывающая сторона (ViewModel находит дубль до вызова и передаёт `rx` с готовым `id`).
- `saveIssue` снимет «В ожидании поступления» — это ожидаемо.

**Отмена выдачи** («Отменить выдачу» в финальном диалоге, §8):
- удалить выдачу (`issueDao.delete`) + tombstone `entityType = "issue"` — по образцу `IssueFormViewModel.delete`;
- вернуть рецепту статус `ISSUED`, **только если** у него не осталось других выдач (`forRx` пуст) и текущий статус `REDEEMED`;
- «В ожидании поступления» **не восстанавливать** (принятое поведение, §13 п.12).

- **Нет назначения** — создание на месте: подбор из справочника или `DrugCreateDialog` (лежит в `PrescriptionEditScreen.kt`), предзаполненный названием из OCR (`rpName`, при пустом — первая `drugLine`), размером упаковки из «№» и видом «устройство», если в `formName`/названии встречаются слова «полоск/набор/штрич/шприц/помп/сенсор»; затем **обязательная форма нормы** с `validFrom` = дата рецепта (редактируемая), Signa — подсказкой над формой. - **Диалог подтверждения** перед выдачей: «5 × №50 = 250 шт, дата ДД.ММ.ГГГГ», предпросмотр «обеспечен до» через `IssuePreview.afterIssue` (Ф10, на чтение), затем `RxIssuePlan.blocks` (кнопка «Выдать» недоступна) и `warnings`. Диалог обязателен: OCR ошибается, числа должны пройти ручную сверку.
- **Финальный диалог**: «Выдано. Обеспечен до …» и кнопки «Готово» / «К назначению» / «Отменить выдачу» (§7).
- После выдачи рецепт со статусом REDEEMED исчезает из списков «выписан» (`allIssued`/`observeAllIssued`) и из строки «Просрочено рецептов» (Ф12) — проверить, что это нигде не ломает списки и сводку.

## 12. Чек-лист приёмки

Статусы: **выполнено (чем подтверждено)** / **не проверено — нужна проверка заказчиком на устройстве** / **не выполнено (причина)**.

1. Скан бланка с «Количество единиц» и Dtd № → поля предзаполнены, правятся вручную.
2. «Сохранить и выдать»: диалог сверки (кол-во, дата, предпросмотр, предупреждения) → подтверждение → в журнале выдача датой рецепта, «P уп × K» при совпадении упаковки, штуками — при несовпадении, «обеспечен до» пересчитан.
3. Рецепт после выдачи — «отоварен»; отсутствует в «выписан»/«просрочено»; после «Отменить выдачу» выдача удалена, статус вернулся «выписан», дубль-проверка снова пропускает.
4. Дубль: повторный скан того же бланка → блок «уже есть выдача»; рецепт без выдачи переиспользован (новой записи нет).
5. Пустые серия/номер — проверка отключена, показано предупреждение; номер с пробелами при ручном вводе — дубль находится.
6. Старый путь: «Сохранить рецепт» → «Выдать» — форма с датой рецепта и предвыбранным рецептом, статус «отоварен», дубль-проверка видит эту выдачу.
7. Отсроченное: тумблер/штамп → предупреждение, дата выдачи = дата рецепта.
8. Просроченный рецепт → предупреждение, выдача разрешена; будущая дата → блок.
9. Создание назначения на месте: диалог позиции предзаполнен (название, № упаковки, вид), форма нормы с `validFrom` = дата рецепта, Signa — подсказка; выдача прошла после сохранения нормы.
10. Регресс: обычный «Сохранить рецепт», форма выдачи, «Срочное», документы, все 102+ тестов зелёные; после Ф13 — новые из §11.

## 13. Принятые решения (фиксированные, отступать нельзя)

1. Выдача — только по кнопке «Сохранить и выдать» с диалогом подтверждения; автогенерации нет.
2. Штуки = единицы × №; при несовпадении упаковки — запись штуками с предупреждением (не «перекладывать» в упаковки делением).
3. Назначение создаётся на месте; норма обязательна, `validFrom` = дата рецепта, редактируемая; Signa — только подсказка.
4. Дубли — по серии+номеру без пробелов; блокировка при существующей выдаче; переиспользование без выдачи.
5. Отсроченное — датой рецепта + предупреждение; детект «ОТСРОЧ» + ручной тумблер.
6. Просроченный — предупреждение; будущая дата — блок (Ф1.5).
7. Норма автоматически не создаётся и не меняется для существующих назначений.
8. Выдача позже даты рецепта — предупреждение без блокировки (по словам заказчика, случай невозможен на практике).
9. **Статус после выдачи — «отоварен» (REDEEMED)** — решение заказчика от 01.11.2026 («пусть будет статус отоварен»), единообразно с п. 3.5 ТЗ 1.1 и `IssueFormScreen`. Отмена возвращает «выписан» при отсутствии других выдач по рецепту.
10. Regex из черновика беседы исправлены ревью: метка «Выписано Вр.», символьные классы вместо квантификаторов после кириллических букв, значение метки сначала на той же строке; `D.t.d.` tolerated.
11. Дубль-проверка закрывает и старый путь «Выдать» (передача `rxId` через маршрут); при пустых серии/номере отключена.
12. «В ожидании поступления», снятый выдачей, при «Отменить выдачу» не восстанавливается.
13. Дубль-рецепт у другого пациента — предупреждение без блокировки.
14. `versionName` 1.4.0; тег `v1.4.0` — после подтверждения блоков A–B–C.
